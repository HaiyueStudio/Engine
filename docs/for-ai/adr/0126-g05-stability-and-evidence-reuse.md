# ADR 0126：G05 稳定性调查与按输入哈希复核证据

- 状态：接受；2026-10-13 用户明确批准两项调整。
- 后续调整：[ADR 0127](0127-forward-cpu-investigation.md) 仅将 Forward CPU 5% 改为调查项；本页保留当时决定，其余要求继续有效。
- 具名例外：[ADR 0129](0129-readback-repair-evidence-reuse.md) 仅允许一次 readback 夹具修复后复核固定的六组，完整正确性重采；本页原决定保持。
- 取代范围：[ADR 0125](0125-g05-continuous-sampling.md) 的 G05 跨轮稳定性硬门禁，以及 0.2.1 专项证据仅因验收/文档提交号不同就必须重采的要求。采样协议和旧结果保留。
- 执行入口：[0.2.1 证据策略](../../../scripts/engine-021-evidence-policy.mjs)与[独立复核](../../../scripts/check-engine-021-evidence.mjs)。

## 问题

跨轮低耗时波动可以使完整且满足原性能预算的矩阵整体失败；这项波动本身不能证明生产卡顿。另一方面，仅修改验收解释或文档会改变提交号，却不会改变执行中的运行时、采样器和画质。无条件整组重采增加操作成本，也容易演变为择优保留数据。

## 结论

G05 三轮稳定性继续完整计算和报告，超线作为调查项，不再单独阻断性能预算验收。原 Forward 5% 回归预算、多灯与实例绝对/相对性能预算、像素容差、资源上限、覆盖和清理要求全部保留。生产帧节奏与持续资源证据仍独立必需；持续且影响目标的退化不能由本决定豁免。此决定不改变其他独立性能合同。

仅当变更局限于说明文档或本专项的验收解释，且运行时、采样器、测量配置和全部候选可执行构建产物哈希一致时，允许复核既有完整证据。采样提交和验收提交分别列出，均须干净。原始报告、原失败判定和原始文件不改写、不拼接。

## 解决方法

1. 原连续采样入口继续输出原统计及原判定；新验收层重读全部原始捕获、来源登记、像素、资源和原始预算，生成单独评估。缺失、非法、脏来源及不完整矩阵不能降级成警告。
2. 完整保留三轮 P95、spread、CV 和每项稳定性失败；不给慢样本设删除规则，不自动重试，不仅选择最快轮次。稳定性调查不自动归因于 CPU/GPU 频率或驱动。
3. 证据清单使用 `engine-021-evidence-v2`：验收 `revision`、七类报告路径/SHA-256/`captureRevision` 必须显式绑定。七类仍为正确性、生产帧节奏、资源长跑、消融、G05 房间、实例与 Forward。
4. Git 比较必须证明两提交仅涉及 Markdown 说明文档或具名的三个专项验收文件。任何运行时、采样器、依赖、测量配置或构建脚本变化均要求新采样；同时核对完整输入指纹，不能用“代码看起来一样”代替哈希。
5. 从验收提交重新构建四个候选夹具入口，逐一比较全部可执行 chunk；正确性与 G05 共享相同基础入口。另核验正确性使用的包产物与固定基线、Forward 固定来源及全部已登记原始构建文件。旧产物摘要不能替代新构建。
6. 独立评估同时记录原判定、验收判定、警告、采样/验收提交、Git 差异与新构建哈希。复核通过仅满足专项前置条件，不自动完成 G05/G09/G07，也不代替 Shader、生命周期、独立包和其余发布链。

当前数值、剩余项和证据路径统一维护在 [0.2.1 验收结论](../../../review/engine-0.2.1/README.md)，不新增逐次运行的过程文档。
