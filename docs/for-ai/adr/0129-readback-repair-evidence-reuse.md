# ADR 0129：读回诊断修复后的六组限定复核

- 状态：接受；2026-10-17 用户明确批准此次限定复用。
- 后续具名例外：[ADR 0130](0130-pbr-windows-reference-evidence-reuse.md) 单独批准 Windows 页面参考修复及固定七组复核；本页原决定保留。
- 调整范围：[ADR 0126](0126-g05-stability-and-evidence-reuse.md) 第 4 条的一次具名例外；默认复用规则与全部验收预算保持。
- 执行入口：[具名报告与修复字节](../../../scripts/engine-021-evidence-policy.mjs)、[原始数据独立复核](../../../scripts/check-engine-021-evidence.mjs)。

## 问题

包含 Toast 的干净候选 `384ad34d7007b0618cdd0408f3968d5085461130` 完成七组采样及全量原始数据复核。后续全局门禁中的 readback/churn 夹具在 owner 释放后读取缓存诊断记录，而追踪器按设计在释放时清理这些记录，产生零命中／未命中的误报。修复只在每个 owner 释放前保存真实缓存活动；资源残留继续从全部清理后的快照读取。

## 结论

仅允许复核复用该采样提交下已经完整完成的生产帧节奏、资源长跑、消融、G05 房间、实例和 Forward 六份报告。报告路径和 SHA-256、修复夹具／辅助模块／回归测试的字节哈希均在执行策略中固定，不接受其他报告替换或后续夹具变更。该例外不是一般性的测试代码变更豁免。

完整正确性报告登记了夹具目录，因此修复后必须重新采集全部 224 项。全局发布门禁、独立发布包及无发布演练仍须完整执行；六组复核和短／长 readback 通过不能授予发布资格。

## 解决方法

1. Git 差异仅允许固定的三份 readback 修复文件、ADR 0126 的三个具名验收文件、`engine-021-candidate-policy.mjs` 及其测试、`review/engine-0.2.1/release-candidate.json` 的候选元数据与说明 Markdown；其他运行时、采样器、依赖、配置或构建变化继续要求新采样。
2. 六份原始报告保持原字节和原失败判定。新清单显式绑定本决定、旧采样提交、新验收提交、完整报告路径及原 SHA-256，不能拼接轮次、删除慢样本或重写报告身份。
3. 独立复核仍重读全部原始捕获、像素、资源和原预算；六组各自的采样输入、配置、主机、运行时指纹必须与当前一致。从当前提交重建四个夹具入口，逐一核对全部可执行块。
4. 当前正确性必须是新的完整干净捕获。readback 的 120／1800 帧、两槽读回、释放取消、零残留、缓存命中／未命中要求全部保留；只调整诊断采集时机。
5. G05 跨轮稳定性与 Forward CPU 5% 仍按 [ADR 0127](0127-forward-cpu-investigation.md) 单列调查；GPU 5%、其余性能预算、画质和资源要求不变。不发布版本，不晋升基线。
