# 固定八帧上限的延长观察诊断

本轮准备 `g09-bounded-batch-completion-long-v2`，独立采样尚待执行。它用于检验双方在较长观察下的逐帧等待与批量完成差异，不建立基线、不授予性能资格，原 5% 回归预算保持。

## 为什么延长

[上一轮完整结果](batch-completion-full-result.md)的 B8 仅覆盖约 12 秒，S8 约 66 秒，且记录到两次会话锁屏。旧结果完整保留，不能证明持续慢段消失。用户已取消屏保恢复登录，并关闭 Chrome、Edge。新入口检查屏保、锁定策略、事件审计可读性和当前会话；完整运行期间任何锁屏都会使该批失败，即使之后解锁。

## 固定设计

- A0/B4、S8/B8 每次均固定 **120000 个 GPU 测量帧**，120 帧 GPU 预热。固定双轮反向平衡顺序共 8 次，总计 960000 测量帧。
- 顺序为 A0/S8、B4/B8、A0/B8、B4/S8、B4/S8、A0/B8、B4/B8、A0/S8。
- 每次完整捕获必须至少覆盖 **90 秒**，按首个测量批提交至最后测量批完成围栏的区间计时。时长不足记录为证据不足；不延长、不重试、不删除样本。固定人口保留 500 个 240 帧相机周期和 400 个 300 帧窗口。
- CPU 18000 帧预热、3000 帧测量，120 秒冷却及原安静检查、200 ms GPU 遥测均保持一致。
- 两组共用 8 帧在途上限、8 槽/16384 字节读回缓冲、每帧提交与时间戳复制、每批完成围栏和读回。下一批须等待前批完成、读取和解映射。唯一主动变量仍是采样器的逐帧显式等待；引擎每帧退休通知保留。
- ETW 与频率归属均使用双方一致的整批提交到完成区间；不能据此归因到批内某一帧。
- 保留 Chrome 专属最高性能偏好与临时 CPU 最低状态 100%，结束或失败自动恢复原配置。这不是 GPU 锁频。服务设置不变。

90 秒门槛覆盖此前约 59–63 秒才出现的慢段，但不构成长时间稳定性资格。固定帧数仍意味着双方运行时长不同；若 S8 未重现慢段，B8 没有慢段的结果也不足以确认原因。

## 工程验证与修复

入口采用 Windows 自带 PowerShell 的绝对路径；跨旧、新入口共享独占保护。修复只读 `-Plan` 进程被误判为采样任务的问题，真实旧/新采样任务仍阻止重复启动。

首两次容量工程检查保留 failed：页面报告 complete 后调试接口读取超时。分块传输单独应用后仍复现；随后让结果节点仅在测量结束后隐藏，避免大 JSON 文本的页面排版，再配合分块读取和长度验证。此前短协议、生产浏览器执行器与历史证据未修改。该修复不改测量帧和 GPU 同步行为；超时定位由该工程对照支持，不当作性能归因。

最终工程容量验证：A0/B8 97.235 秒、B4/B8 102.872 秒，各保留 120000 测量帧、120120 次提交/引擎通知、15015 次批完成/读回，400 个固定窗口完整；各原始结果约 106–107 MB，资源清理通过。30 项专项测试通过，含分块 Unicode 完整性、短块拒绝、旧/新入口防重和只读计划豁免。

[机器复核记录](batch-completion-long-checks.json)绑定最终源码、双方各 120000 帧容量验证、四组短矩阵、追踪启动后的故障恢复、防重与复用测试、主机最终状态及仓库检查。在线工程容量检查使用缩短的 CPU 准备，Codex 仍开启，只验证大结果保存、逐帧完整性与清理，不进入性能验收。

## 执行入口

以管理员身份运行：

```text
D:\HaiyueStudio\Engine\artifacts\engine-0.2.1\g09\start-gpu-batch-long-safe.cmd
```

出现“后台诊断已准备好”后点击确定，退出 Codex 和启动窗口；保持桌面空闲、不锁屏。不要开启浏览器或任务管理器，不要重复启动。预计 **70–100 分钟以上**，以最终完成弹窗为准；窗口关闭不代表采样完成。

D 盘启动要求至少 40 GiB 可用空间，保留原始 ETW 和全部样本。页面执行超时 15 分钟、单个外层捕获 20 分钟；完整八次结束后先恢复设置，再分析数据，最终通知在恢复和分析完成后显示。入口预检失败时不改电源设置。

后续先确认全部 8 次的未锁屏条件、每次 90 秒暴露、S8 是否复现及 B8 是否仍有慢段，再关联核心频率和整批调度记录。只有机制得到双方一致支持，才讨论生产策略与全新同机基线；5% 门禁不作放宽。
