# 独立 GPU 调度归因与采样器修复验证

2026-10-09 的独立 A0/B4 调度诊断完成。已定位两个不同现象：最终输出尖峰与 Windows 桌面 GPU 活动高度相关；整段耗时突然变快与采样 Chrome 在启动约 120 秒后创建的信息收集 GPU 进程同时发生。追加的单参数工程对照中，该进程和 P0 升频均未再出现。独立反证和完整性能资格尚未完成，原 5% 回归预算不变。

## 独立记录完整性

目录为 `artifacts/engine-0.2.1/g09/gpu-scheduler-closed-20261009T111159Z`，本地 19:12:00–19:23:21。固定执行 A0、B4 各一次，沿用 CPU 18000 帧预热 / 3000 帧测量、GPU 120 帧预热、120 秒冷却和三次 CPU ≤5% 的安静入口检查；每项保留 15000 个 GPU 测量帧，分为五十个固定 300 帧窗口。

[独立复核](gpu-scheduler-result-checks.json)验证运行时/源码、原生 Chrome/设备、原始样本、完整窗口、进程记录及恢复日志。319 次进程观察未发现列出的 Codex、VS Code、Epic、Steam、任务管理器等后台程序；每次最多 1 个进程元数据不可读。CPU/GPU 临时设置恢复，本次拥有的跟踪会话停止，Windows Search 状态保持。

原始 ETL 全部保留，解码覆盖完整 GPU 阶段，A0/B4 分别取得 117102 / 117074 个调度事件。最初按尖峰组合 XPath 的查询因条件过多失败，空目录保留；随后成功解码整个阶段，没有删除异常帧。以 GPU 上下文与提交序号共同解析所有者；同一系统队列有多个提交进程，仅使用地址会误报歧义。增加提交序号后两组分别有 17021 / 17013 个队列键，歧义均为零，原“不得存在歧义”断言保留并通过。

## 变频来源：采样 Chrome 的延迟信息收集

| 版本 | 浏览器 PID | 正常渲染 GPU PID | 信息收集 GPU PID | 距浏览器启动 | 信息收集进程存活 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A0 | 5560 | 8320 | 2864 | 120.239 秒 | 527 ms |
| B4 | 12744 | 9980 | 15512 | 120.206 秒 | 515 ms |

两次短进程都属于对应采样 Chrome，带有 `--type=gpu-process --use-gl=disabled` 和 GPU 身份参数。ETW 记录了创建、退出及 GPU 提交；正常渲染 GPU 进程持续存活。它们太短，均未出现在一秒一次的进程观察中。明细及原始字节绑定见运行目录下的 `chrome-info-attribution.json`。

两组在短进程提交 GPU 工作后首次观察到 P0 / 核心 1607 MHz；P0 约持续 30 秒，再经 P2/P5 回到 P8。固定窗口 P95 因此从约 1.0 ms 降到 0.29 ms。A0 全部窗口 P95 范围为 0.286720–1.934336 ms，B4 为 0.286720–1.883136 ms；合并全部帧的 P95 约 1.04 / 1.03 ms 并不能表示稳定。

[Chromium 上游实现](https://chromium.googlesource.com/chromium/src/+/70fcec589207d2da1564c8f378ae9c973f4116ee/content/browser/gpu/gpu_data_manager_impl_private.cc)包含延迟 120 秒的 DirectX 信息收集，以及独立信息收集 GPU 进程；[开关定义](https://chromium.googlesource.com/chromium/src/+/main/gpu/config/gpu_switches.cc)提供 `--disable-gpu-process-for-dx12-info-collection`。这些源码用于解释机制，并未声称与本机 Chrome 154.0.8037.99 二进制一一对应；本机行为由上述 ETW 和后续实测验证。

## 输出尖峰：桌面 GPU 活动相关

以输出 pass 超过 0.4 ms 作为诊断分组，A0 36 帧、B4 27 帧，共 63 帧，全部观察到 `csrss` 或 `dwm` 的 GPU 包与采样 Chrome 的 GPU 包时间区间重叠。普通帧仅 141 / 29937 帧存在其他上下文重叠；只比较 P8 中普通帧，比例为 51 / 13969。全部测量帧仍参与原始统计，0.4 ms 不是验收剔除阈值。

这说明桌面调度干扰值得优先处理，不能将这些尖峰直接认定为 B4 新增着色器开销。包时间重叠尚不能证明某一次硬件抢占：Chrome、csrss、dwm 的上下文 NodeOrdinal 分别涉及 9、0、0/6，未建立虚拟节点与物理执行单元的完整映射，也没有将每个 GPU pass 起止精确换算到 ETW 时钟。系统光标闪烁周期读回为 530 ms，与部分桌面任务的周期接近，但尚未证明具体窗口来源。

## 单参数工程对照

工程目录 `artifacts/engine-0.2.1/g09/gpu-info-control-engineering-20261009T115211Z`，采用诊断副本，仅增加关闭 DX12 信息收集的 Chrome 参数，原共享 runner 和 Engine 源码不变。仍保留 18000 / 3000 CPU 帧及 15000 GPU 帧，追加 ETW。

采样 Chrome 存活 155.145 秒，ETW 中只出现一个正常渲染 GPU 进程，未出现原 120 秒信息收集子进程；全部 GPU 测量窗口均为 P8，没有原先 P0→P2→P5 的切换。电源和跟踪会话正常恢复。

本次 Codex 在线，属于工程验证。输出 pass 仍有 14 帧超过 0.4 ms，窗口 P95 最大仍为 1.898464 ms，核心频率也有局部变化，因此不能宣称全部稳定性问题已解决，更不能形成新基线。它支持先修正采样器，再在独立环境确认的路径。

## 已准备的独立反证入口

管理员运行 `artifacts/engine-0.2.1/g09/start-gpu-info-control-with-codex-closed.cmd`。窗口启动后台任务后自动退出；若从已有命令窗口运行，也请关闭该窗口。随后退出 Codex、浏览器及任务管理器，保持桌面空闲且不锁屏，约十分钟后完成，入口安静等待可能延长。

后台固定运行一次 A0、一次 B4，关闭同一项延迟信息收集。通过隐藏本次启动控制台，减少控制台光标/重绘活动；不会关闭或终止 Windows 桌面进程，不修改用户的全局光标、屏保或驱动设置。结果写入新的 `gpu-info-control-closed-*` 目录；启动日志在 `gpu-info-dispatch-*` 下。

复核顺序预先确定：确认真实浏览器命令行、120 秒后信息收集进程是否消失、全部固定窗口频率、输出尖峰及桌面任务重叠，再决定是否具备重建完整基线的条件。保留所有失败，不自动重试，不挑窗口、删异常或按频率折算耗时。

[工程与入口检查](gpu-info-control-checks.json)绑定长工程捕获、隐藏入口正常试跑、跟踪启动后的故意失败恢复及最终状态。原 [v4 全量失败](controlled-gpu-v4-result.md)仍为 failed；正式 GPU 人口 300 帧、回归预算 5%、跨轮 spread/CV 上限 20%/10% 均保持。独立反证通过后，才可版本化采样条件并重新校准、冻结和全新采样；此处没有提升性能资格。
