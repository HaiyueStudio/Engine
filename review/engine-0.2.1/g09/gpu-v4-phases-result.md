## 尖峰已经缩小到哪个阶段

第二个 B4 捕获的第 1800–2099 测量帧窗口 P95 为 **1.310688 ms**。其中第 1929–2092 帧范围内有 17 个总耗时超过 1.2 ms 的帧，集中在本地约 18:23:01.384–18:23:02.063。

异常主要来自 `SceneOutput.renderPass`：正常帧该 pass P95 为约 **0.158 ms**，这 17 帧中的范围约 **0.537–0.720 ms**。场景主 pass 没有同幅度增长；这些异常帧的 CPU P95 约 0.570 ms，与全段 0.565 ms 接近。同期频率观察保持 P8 / 核心 556 MHz / 显存 405 MHz，没有观察到热降频标记。

此类输出尖峰也出现在第一个 A0 捕获的两帧和第一个 B4 捕获的一帧。A0 修订与当前版本的 `engine/src/postprocess/SceneOutputPass.ts` 无差异。代码检查还确认基准输出到 `createAuditTarget` 创建的离屏纹理，不是直接呈现到显示器的 canvas。因此当前证据不能认定是 FrameGraph 新增着色器回归，也不能把它直接命名为本程序的呈现等待。

17 / 300 超过 5%，足以抬高该窗口 P95；17 / 2400 则低于 1%，合并后 P95 看似正常。增加 GPU 样本数量会掩盖这一段高尾，不能作为验收修复。尖峰出现在预热后的第七个固定窗口，也不支持继续单纯延长前置预热。
