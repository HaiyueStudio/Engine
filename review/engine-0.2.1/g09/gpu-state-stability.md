## GPU 失败的位置

八灯 A0 三轮各保留完整 300 个 GPU 样本：

| 轮次 | GPU pass sum P95（ms） | GPU span P95（ms） | 捕获结束 GPU 核心频率（MHz） |
| --- | ---: | ---: | ---: |
| 1 | 1.024000 | 1.119232 | 531 |
| 2 | 1.030144 | 1.126400 | 531 |
| 3 | 0.288768 | 0.293888 | 1607 |

pass sum 的 spread 为 72.40%、CV 为 44.57%；span 的 spread 为 74.38%、CV 为 46.16%，超过既有 20%/10% 稳定性上限。合并 GPU 比值虽为负回归，基线仍不合格。第三轮 300 帧全部在较快区间，sum 为 0.234496–0.294912 ms，不是少数孤立离群点。

三轮的已有 CPU 阶段工作量记录相同：每帧平均 8.899667 次 draw、3 次 render pass、272 字节上传、pool miss 为 0；GPU 计时均包含相同三个 pass 标签。没有 validation 错误或资源残留。已有工作量记录主要来自 CPU 测量阶段，因此仍需补齐 GPU 计时阶段的逐帧细节，不能单凭这些计数排除一切 GPU 执行差异。

校准阶段还出现两次同类低耗时/高结束频率：

| 捕获 | GPU pass sum P95（ms） | 结束频率（MHz） |
| --- | ---: | ---: |
| 单灯 B4，第 2 轮 | 0.145408 | 1607 |
| 单灯 A0，第 3 轮 | 0.184320 | 1278 |

其余 21 次计时捕获的结束频率为 265–594 MHz，GPU sum P95 约 0.957–1.049 ms。现象同时出现在 A0/B4，证据强烈指向 GPU 运行状态差异，尚不足以证明动态调频解释了全部变化。特别是另一次正常 B4 捕获在开始时为 1607 MHz、结束时为 278 MHz：前后快照不能代表 GPU 计时窗口内的状态。

48 次主机前后检查全部通过，CPU 0.187%–9.766%；4231 次进程观测未见可读取的 Codex/ChatGPT、VS Code 或 Epic，每次最多 2 个进程不可读取。v3 统一了 CPU 电源条件，但没有连续记录 GPU 核心/显存频率或 P-state，也没有 GPU 稳态校准。这正是当前证据缺口，不能直接延长 GPU 预热到有利窗口后宣称通过。[离线分析](../../../artifacts/engine-0.2.1/g09/unattended-controlled-v3-20261007T095253Z/gpu-stability-analysis.json)和[检查索引](gpu-stability-checks.json)保留全部样本及哈希。

## 下一步定向诊断

[GPU 独立诊断入口](../../../artifacts/engine-0.2.1/g09/start-gpu-state-with-codex-closed.cmd)预登记单一八灯场景的 A0–B4、B4–A0、A0–B4 六次捕获，约 6–8 分钟：

- 各次沿用 6000 帧 CPU 预热、3000 帧 CPU 测量和 120 帧 GPU 预热；随后记录完整 2400 帧 GPU 过程，按固定的八个 300 帧窗口展示，首 300 帧单独保留。
- 每 200 毫秒只读采集 GPU 核心/显存频率、P-state、温度、忙碌率、功耗及降速标志；逐帧保存 GPU pass sum/span、各 pass 时长、CPU/queue wait 和同机 UTC 时间边界。时间对应是窗口级观测，不冒充每次 draw 的精确时钟证明。
- 固定 15 秒诊断间隔，仅为短期状态调查，不替代正式 120 秒冷却人口。全部捕获结束并恢复 CPU 电源后才离线分析，不重试、不补样、不按结果择窗。
- 完全退出 Codex 后启动，共用既有临时 CPU 最低状态 100% 方案并自动恢复；GPU 设置和 Search 均不修改。读取当前应用时钟接口返回 N/A，没有据此尝试未经验证的 GPU 锁频。
- 记录、绑定和原生清理复用既有夹具、固定 A0/当前 B4 bundle 与 Chrome helper；所有结果标注 diagnostic-only，不生成新的验收基线。

先完成这一状态诊断，再决定共同 GPU 条件及其验证方法；本次尚未修改正式合同或新增豁免。
