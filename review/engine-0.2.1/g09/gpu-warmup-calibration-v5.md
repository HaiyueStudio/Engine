# G09 共同 GPU 预热与新同机基线（v5）

2026-10-12。依据独立长诊断中 B8 的稳定结果及 A0/B8 首窗过渡问题，新增采样协议 `g09-forward-cold-steady-v5`。本阶段重建同机开发基线；不授予完整 G09、G05/G07 或发布性能资格。v4 配置及原始失败、诊断证据保留。

## 冻结的规则

- 两场景仍为 `forward-small-1`、`forward-cap-8`，保留原场景及后处理。A0 固定历史提交，B4 使用当前已绑定构建；三轮顺序仍为 AB / BA / AB，每次间隔至少 120 秒，并要求三次 CPU ≤5% 的空闲观察。
- CPU 阶段保留逐帧执行与原有统计定义。冷启动使用新浏览器配置、新设备，在独立记录场景准备和管线编译后取前 120 个 CPU 运行帧；不声称清除了系统或驱动缓存。完整 CPU 校准仍为每次 24000 帧，候选 1200 / 3600 / 6000 / 12000 / 18000，稳定窗口为 3000 帧。
- GPU 阶段双方均采用 B8：最多八帧在途，共用八槽、16 KiB 读回环；每帧一次提交，批末一次完成等待和一次映射。只省略基准自身的逐帧显式等待，引擎资源回收通知保持原样；阶段末不足八帧也完整读回。
- 另行采集完整的 12 次 GPU 校准，每次 10200 帧全部保留。预先登记候选 120 / 600 / 1200 / 2400 / 4800 / 9600；不依据 A0/B4 加速比挑选预热长度。
- 对每个候选，两场景、双方、全部三轮的 GPU pass sum 与 GPU span 都必须稳定：之后每个 300 帧窗口的三轮 P95 满足原 20% spread / 10% CV；相邻窗口、所有后续窗口对首窗的汇总和逐轮 P50/P95 漂移均 ≤5%。末尾若不足整窗，额外覆盖最后 300 帧，保留重叠边界，避免漏查末段变化。
- CPU 与 GPU 的共同边界均通过后，写入不可混用的冻结记录及校准哈希，再启动 12 次全新基线捕获。每次比较全部 3000 个 CPU、300 个 GPU 测量值，不从诊断或校准尾部抽取基线，不自动重试或删除异常帧。
- CPU/GPU P95 原 **5% 回归预算不变**；帧墙钟仍要求稳定，冷 CPU 指标继续单独报告。临时 CPU 电源方案与 Chrome 专用 GPU 偏好一致，GPU 偏好不等于频率锁定。双方采用相同的 DX12 信息收集关闭选项。

## 正确性与启动

性能采集前，每种场景、每方均执行 S8/B8 完整画面对照，同时比较 A0/B4：GPU 预热 5 帧、测量 19 帧，覆盖八槽回绕及阶段尾批。每帧原始时间戳、提交、回收、批次完成与读回关系均校验。

独立入口为工作区根目录 `start-g09-calibration.cmd`；仓库内 `scripts/start-framegraph-unattended.cmd` 也转发至同一入口。先完全退出 ChatGPT/Codex、浏览器、任务管理器、VS Code、Epic、Steam，再从文件资源管理器以管理员身份启动。确认后保持空闲、不锁屏，通常约 80–100 分钟，空闲等待可能延长。

入口在更改设置前检查有效管理员令牌、后台应用、桌面锁屏条件及 A0/B4 构建。隐藏 worker 继承管理员权限，持有与长诊断共用的独占锁；重复启动直接拒绝。每阶段进度写入 `run/measurement/status.json`。退出和失败都保留证据，完成通知在子进程结束及设置恢复检查后发出。

任何 CPU/GPU 校准失败都会阻断新基线。基线采样完成后重新从原始数据计算结果，并核对冻结时序、源文件、构建、主机、电源方案和捕获哈希。最终仍需人工复核本次独立运行；工程短采样不能充当基线。
