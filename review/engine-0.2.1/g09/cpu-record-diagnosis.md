新增三段独立电源对照取得了干预／恢复方向一致的证据：提高交流最低处理器状态后，A0 后半段稳定；恢复原设置后，又出现低性能指标和慢窗口。**处理器电源状态是已验证的重要干扰因素**。底层触发机制与所有残余波动的完整解释仍未闭环。[随后完成的 v3 全量采样](controlled-sampling-result.md)已确定共同 6000 帧预热并得到稳定 A0 新基线，但 B4 单灯/八灯 CPU 回归 5.31%/6.96%，主要增量仍落在 record。历史电源波动与当前回归分别保留，不能把后者一概归为环境。

## 先前在线诊断及反证

- 平衡方案的交流最低处理器状态为 5%。一次细分诊断中，后段处理器性能指标中位数由约 110 降至 87；固定算术探针从约 0.050 ms 升到 0.060 ms，CPU record P95 从 0.400 ms 升到 0.515 ms。多个渲染阶段同步变慢，支持处理器运行状态变化参与了该次抬升。
- 复制原方案、仅将交流最低处理器状态改为 100% 后，性能指标稳定在约 111–112，参考算术中位数维持约 0.050 ms。但 record 仍波动；恢复原方案后的第二次观测也没有重复出现同样严重的降频。因此这里只确认一个环境风险，不能把它当作唯一原因或已通过干预验证的完整解释。
- GC/JIT 的直接暂停不能解释诊断中的大多数后段慢帧。基本 B4 诊断最后窗口的 record P95 为 0.765 ms，152 个 P95 尾部帧中 GC 重叠为 0、JIT 重叠为 1；前一个窗口为 0.485 ms。把增量 GC 事件也纳入后，该结论仍成立。后台并发 GC、代码优化改变后续执行成本等间接影响尚未排除。
- CPU record 的统计范围包括 `Render3DSystem.record()`、GPU 命令接口及已有的资源／绘制统计包装。调用栈热点包含 `encoder.beginRenderPass`、`cacheRenderPassState`、绘制计数包装和场景录制；这些是执行热点，尚未证明其中哪个产生了后段波动。

原闭合采样没有连续处理器性能或逐帧事件时钟。本轮使用 Codex 在线时的诊断，不能追溯证明原失败每一个尖峰的原因。早期基本 B4 诊断还与离线分析工作重叠，记录到其他 `node` 进程约 19.48% 的瞬时 CPU，明确保留这一干扰，不将其当作纯引擎退化。

## 为什么原主机检查没拦住

[Windows 主机检查](../../../scripts/webgpu-gate/framegraph-windows-host.mjs)目前检查捕获前后 CPU/GPU 占用、GPU 状态和电源方案身份；`reportedMHz` 是 `os.cpus().speed` 的报告值，源码明确声明它不是连续频率或 CPU 温度资格。低占用、同一个电源方案与捕获中处理器性能稳定是不同的观测。此次证明需要补充连续证据，不能把原来的 24/24 前后检查解释成整个计时区间完全无干扰。

Windows 性能计数器的类型与采集接口见 [Microsoft PerfLib 文档](https://learn.microsoft.com/windows/win32/perfctrs/using-the-perflib-functions-to-consume-counter-data)。本文保存 `PercentProcessorPerformance` 原值，不将全核心观测冒充当前渲染线程所在核心的精确瞬时 MHz，也不将它和 CPU 忙碌比例混用。
