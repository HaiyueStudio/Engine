## 为什么这次没有通过

隐藏入口原来只报告“已启动”，没有结束通知，约十分钟的预估又没有涵盖安静负载等待。B4 的 42 次负载检查跨度约 224 秒，随后开始测量；用户重新打开 Codex 时，采样尚未完成。这是入口反馈不足，不能把启动器窗口结束当作整批结束。

本轮实际从 20:02:32 运行到 20:18:20。A0 的 157 次进程观测没有指定后台应用；B4 的 157 次观测累计记录 2355 个 ChatGPT/Codex 进程出现项（不是 2355 个不同进程）。B4 的输出尖峰及 P0/P2/P5 状态受该条件影响，不能用于验证修复效果。所有 B4 数据和失败原因保留。

CPU 临时电源方案已移除，Chrome GPU 电源设置已恢复，Windows Search 状态与启动前一致，所属跟踪会话已停止。20:38 的补充读取确认无本轮采样工作进程、无所属跟踪会话残留；完成通知窗口如果尚未确认，仅是提示窗口。

## A0 验证了什么

关闭 Chrome 延迟 GPU 信息收集的参数确实生效：ETW 生命周期记录中仅有一个正常渲染 GPU 进程，没有原来约 120 秒后短暂出现的额外信息收集进程。A0 测量阶段的 297 次设备观测全部为 P8、显存 405 MHz；没有再出现旧诊断中由该信息收集进程伴随触发的 P0。

但这还不足以取得稳定性资格。A0 首个 300 帧 GPU 合计 P95 为 1.021952 ms，全部 15000 帧为 1.040384 ms；50 个连续 300 帧窗口的 P95 为 1.004544–1.890272 ms。合并所有帧得到一个接近的 P95，不能消除局部波动，更不能替代正式人口。

剩余现象分为两类：

1. 10 个输出阶段超过 0.4 ms 的尖峰，均与外部 GPU 调度包重合：9 个涉及 dwm，1 个涉及 csrss。这是主机时间上的重合，不能单独证明具体抢占机制。隐藏控制台后数量比前次少，但两批条件并非只差一个变量，不能据此证明全部来自光标或控制台。
2. 两个主绘制高耗时段，共 139 帧，没有记录到外部 GPU 调度包重合。完整事件复核也未在这两个 300 帧窗口中发现所列分页、换入换出或显存用量变更事件。

相邻正常窗口记录了分页事件，慢窗口却没有，现有证据不支持把此次连续慢段直接归因于显存换页。采集配置的覆盖范围有限，不能据此排除驱动内部的驻留或电源管理。

## 当前结论与下一步

延迟信息收集进程这一干扰源已有独立 A0 反证；主绘制的短时持续波动仍未归因。本轮没有修改引擎实现、共享验收采样协议或正式门限，也没有把诊断数据升级为新基线。历史 v4 失败继续有效。
