# Windows 性能验收的主机干扰归因

日期：2026-10-06。完整 Forward 前置回归现已取得 12/12 次捕获、通过全部 24 次主机检查，最终判定仍因旧基线八灯 CPU 轮次不稳定而失败。以下保留主机干扰的定位与修复过程；G09 的 F0–F8 资格尚未完成。最新原始证据及复核见[解决进展索引](../../../artifacts/engine-0.2.1/g09/windows-performance-resolution.json)。

## 取得的证据

在用户已经授权的临时暂停 Windows Search、结束后恢复的范围内，连续记录 138 个约一秒窗口的系统和逐进程 CPU。Windows Search 已恢复 Running/Auto。采用同一个常驻观察进程，记录 PID、进程创建时间和 CPU 累计量，避免反复启动监控；观察进程在启动阶段之后的总 CPU 占用 P50 为 0.192%、P95 为 0.769%，采集本身最大耗时 27.16 ms。

同时运行六次 A0/B4 单灯 Forward 诊断，每次保留 120 帧预热、300 CPU/300 GPU 样本，但间隔仅 10 秒，未执行完整三轮两场景人口或整幅像素预检，因此明确不用于性能资格。归因用的是与主机检查重叠的进程窗口，不能反推此前失败轮次。

| 诊断时点（北京时间） | 原主机检查 | 重叠进程窗口 | 含义 |
| --- | --- | --- | --- |
| 20:51:41–42，第五次捕获前 | CPU 22.482% | Codex 界面 `ChatGPT.exe` PID 14956 在 20:51:41.638 窗口占总 CPU 17.508%；该窗系统总 CPU 21.923% | 桌面应用界面活动足以冲破 15% 空闲阈值 |
| 20:52:06–07，第六次捕获后 | CPU 15.400% | `EpicGamesLauncher.exe` PID 9488 在 20:52:07.026 窗口占总 CPU 12.521%；该窗系统总 CPU 20.192% | 后台启动器也会干扰后测；仅暂停索引不够 |
| 20:49:59，诊断启动阶段 | 非正式前后测窗口 | VS Code 扩展宿主 PID 17460 占总 CPU 17.184% | 编辑器后台活动也是需要隔离的来源；不将此窗冒充捕获失败的直接原因 |

进程身份经可执行文件路径与 VS Code 既有日志核对：PID 14956 属于当前 `OpenAI.Codex` 安装的 renderer；PID 17460 为已打开 HaiyueStudio 工作区的扩展宿主；Epic 以 `-silent -launchcontext=boot` 后台启动。这些是现有应用活动，不是 Engine 测试遗留进程。

原始逐秒记录、六次捕获、阶段时点、服务恢复和诊断脚本快照的 SHA-256 见[诊断索引](../../../artifacts/engine-0.2.1/g09/host-trace-20261006T124955/diagnosis.json)。进程窗口与主机检查不是完全同起止时间，数值不应直接相减；短寿命进程也可能没有两端观测。

## 已落实的主机隔离

1. 用户已自行退出 Epic 与 VS Code；完整入口检查确认三个相关进程名均不存在。此前准备的应用退出包装器未执行，也没有在采样后擅自重新打开用户自行关闭的应用。
2. 采样期间将 Codex 最小化，并使进度显示避开实际采样窗口。当前 Codex 是任务控制进程，不终止它。
3. 使用[采样与逐进程记录包装脚本](../../../artifacts/engine-0.2.1/g09/diagnose-host-load.ps1)的 `-Full` 入口。发现单次 `StopService` 后 Search 会在采样中重新启动，因此改为仅在本轮临时禁止启动并停止，在 `finally` 恢复原 StartMode、Start、DelayedAutoStart 和运行状态；采样结束前检查仍为 Stopped/Disabled。原值及恢复值均为 Running/Auto、Start=2、DelayedAutoStart=1，另作独立查询确认。
4. 完整入口仍为 `verify-framegraph-forward.mjs --full`：同一注册主机、原 A0/B4、三轮 AB/BA/AB、各 300 CPU/GPU 样本、120 帧预热、每项实测至少 120 秒冷却、CPU ≤15% / GPU ≤10%、原 5% 回归和轮次稳定性预算。新窗口中同步保留进程归因；若仍失败，保留整个失败人口并按实际责任进程继续定位，不补拼旧样本或放宽阈值。

采样入口新增 `capture-not-before` 日志时点，供交互控制端避开实际测量和前后检查窗口；实测冷却、运行时、场景、样本及验证器未改变。定向策略测试、入口语法及 `--plan` 检查通过。

两次失败均保留原始人口及恢复记录，没有补采拼接。

## 预热敏感性与后续口径

完整人口的前段 CPU 样本普遍偏慢，故追加预登记的 120/600/1200 帧诊断，不改变正式 120 帧门禁。[第一次探索](../../../artifacts/engine-0.2.1/g09/host-trace-20261006T141027/warmup-diagnostic.json)使用动态比例 0.25、中重叠八灯，只作探索；随后[按正式静态、高重叠八灯配方的对照](../../../artifacts/engine-0.2.1/g09/host-trace-20261006T141600/warmup-diagnostic.json)直接复用 `G05_FORWARD_CASES` 并核对实际配方：

| 预热帧数 | A0 CPU P95（ms） | B4 CPU P95（ms） |
| --- | --- | --- |
| 120 | 1.390 | 1.350 |
| 600 | 0.695 | 0.905 |
| 1200 | 0.655 | 0.730 |

所有诊断均保留预热原始帧及各 300 个计时样本，间隔只有 10 秒，每个长度仅一组，不能作完整验收或因果归因。数据支持“CPU 结果对预热长度敏感”，尚不足以确定 JIT、GC 或其他启动活动的具体贡献；1200 帧的单次 B4/A0 比值也并未落在 5% 回归范围内，因此不能只延长预热就宣告通过。

### 三轮校准结果

随后完成[18 次三轮校准及独立重算](../../../artifacts/engine-0.2.1/g09/warmup-calibration-review.json)：同一静态高重叠八灯配方，预热长度按三轮轮换顺序 120/1200/2400、1200/2400/120、2400/120/1200，版本按 AB/BA/AB 交错；每次保留 300 CPU/300 GPU 样本及全部预热帧。每项间隔 30 秒，明确不替代正式 120 秒冷却的人口。

采样前固定判据：两版本分别在 1200、2400 帧下通过原轮次稳定性，且每个版本两种预热长度的合并 CPU P50、P95 变化均 ≤5%；不能按哪个 B4/A0 比值更好选择预热长度。

| 预热帧数 | A0 合并 CPU P95（ms） | B4 合并 CPU P95（ms） | 主机检查通过的捕获 |
| --- | --- | --- | --- |
| 120 | 1.370 | 1.405 | 5/6 |
| 1200 | 0.815 | 0.720 | 5/6 |
| 2400 | 0.740 | 0.775 | 5/6 |

六个三轮分组都通过原 spread/CV 判据，但本次校准仍为 **inconclusive**：

- 18 次中有 3 次主机检查失败，全部保留，未删除或补拼。首项失败窗口火绒 `HipsDaemon.exe` 的相邻逐秒 CPU 达 30.73%；可执行路径确认为 `C:\Program Files (x86)\Huorong\Sysdiag\bin\HipsDaemon.exe`。其余失败窗口包含 Codex 界面活动。这些不是 Engine 遗留进程；安全软件未被停止或调整。
- 从 1200 增至 2400 帧，A0 合并 P95 变化为 −9.20%，B4 为 +7.64%，两者都未通过预登记的 5% 稳态平台判据。不能将这些变化直接归因于预热，也不能由这次受干扰人口宣称候选通过或提速。
- 原正式预检的 A0 不稳定结论继续保留；追加诊断不替换原报告。当前既没有可靠依据指认 FrameGraph 实现退化，也没有依据授予性能资格。

## 继续验收的具体路径

1. 在无交互界面活动、后台扫描空闲的时段，由独立终端运行[校准包装器](../../../artifacts/engine-0.2.1/g09/diagnose-host-load.ps1)的 `-WarmupCalibration` 入口；保持安全软件启用，继续记录主机与逐进程负载。它会保存新目录，在 `finally` 恢复 Search；本次原始人口不覆盖。避免在采样窗口同时操作 Codex、构建或运行其他测试。
2. 先获得无干扰的多轮校准；若预热平台仍不成立，再预登记更长的连续 CPU 分块与独立 profiler 诊断，区分启动优化、GC/分配及命令录制成本。先确定 A0/B4 共用的冷启动/稳态边界，再版本化新 G09 采样协议；不能把挑出的末段帧当成旧 G01/G05 120 帧协议通过。
3. 口径冻结后重新建立同机 A0/B4 完整人口，保持 5% 回归、20% spread、10% CV 及原场景和质量要求。正式预检仍为 120 帧、当前仍为 failed；完整 G09 场景、非重叠 CPU 阶段归因、消融、G05/G07 资格是独立未完成项。

最后一次校准后，[独立恢复与进程核验](../../../artifacts/engine-0.2.1/g09/host-trace-20261006T142944/service-verification.json)确认 Search Running/Auto、Start=2、DelayedAutoStart=1，测试进程无残留，VS Code/Epic 仍保持用户关闭后的状态。资料中同时保留了可重新运行的校准脚本快照、全部原始样本、逐秒进程记录与哈希。
