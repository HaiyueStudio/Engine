## 可确认的原因范围与下一步

第三轮单灯 B4 的三个 GPU 阶段同时变慢：相对前两轮，主绘制约 +24.73%、灰度后处理 +23.81%、输出 +20.69%。其 10200 个 GPU 帧耗时约 7.986 秒，其他单灯轮为 7.992–8.066 秒；整个 GPU 阶段的墙钟几乎不变，CPU/批次间隔与 GPU 执行耗时不能混为一项。

这支持“整轮 GPU 状态不同”的待验证解释，但还不能确认核心/显存频率或驱动调度是根因，也不能归因于 FrameGraph 某个特定 pass。原生时间戳、读回和固定构建绑定已通过；缺少的是 GPU 执行期间的连续状态证据。当前 GPU 主机观察仅在捕获前后执行，结束读数在 GPU 阶段结束后约 **5.1 秒**，其中的 1341 MHz 等数值不能当作这一轮的运行频率。CPU 进程观察也不能替代 GPU 调度证据。

下一步先做独立、仅供诊断的单灯 A0/B4 对照：

1. 首轮保持 v5 相同场景、构建、24000 CPU 帧、10200 GPU 帧、B8 上限和读回、三轮 AB/BA/AB、120 秒冷却、电源策略及浏览器选项；双方添加完全相同的连续 GPU 状态观察，并记录观察失败与退出。以每帧时间边界关联 P-state、核心/显存频率、温度、功耗、降频原因，不改变计时人口来争取通过。
2. 预先把观察增加本身标为诊断干预；任何观察器开销和可能改变的 GPU 状态必须报告。每轮同等对待，不能只重跑较慢 B4，也不能选择成功的一轮替换本次失败。若状态差异未解释耗时差，再增加双方一致的 GPU 调度事件诊断，区分外部占用与执行速度变化。
3. 只有在共同干预的效果得到验证后，才登记新的共同条件并重新执行独立校准；校准通过后按冻结边界采集全新三轮同机基线。此次没有运行新增诊断，没有生成 `frozen-protocol.json` 或 `same-host-baseline.json`；不建议直接重复当前完整校准来碰运气。
